# ジョブ起動処理 読解ガイド

対象: `run_job.ps1` から `JobName` に対応する `Invoke-*Job` が呼び出されるまでの起動処理。

この文書の目的は、PowerShell のファイル読み込み、関数探索、ジョブ起動の流れを、実行順に追えるようにすることです。

前提として、ここでは高度な設計判断や SOLID 原則の話はしません。
まずは、**PowerShell がどうファイルを読み、どう関数を見つけ、どうジョブを起動しているか**を理解することに集中します。

---

# 0. 最初に結論

ジョブ起動処理で起きていることを要約すると、次の流れになります。

```text
1. run_job.ps1 が実行される
2. Foundation.psm1 という共通モジュールを読み込む
3. Invoke-FoundationEntrypoint を呼ぶ
4. foundation.config.psd1 を読む
5. foundation.jobs.psd1 を読む
6. JobName = InstalledAppExport に対応する設定を探す
7. InstalledAppExport.psm1 を読み込む
8. Invoke-InstalledAppExportJob という関数を探す
9. & $command -Context $context で Invoke-InstalledAppExportJob を実行する
10. 最後に Close-FoundationRunContext で後片付けする
```

この範囲では、`InstalledAppExport` ジョブの業務処理そのものは深く扱いません。

この範囲で確認する中心は次です。

```text
「JobName = InstalledAppExport」と指定したとき、なぜ最終的に `Invoke-InstalledAppExportJob` が呼ばれるのか。  
また、root の `.bat` が `WeeklyScanTargetSync` や `MonthlyInstallReport` を渡したとき、なぜ Composite Job の入口関数が呼ばれるのか。

root `.bat` と `JobName` の対応だけを先に確認したい場合は、`docs/01_起動設定/bat起動入口とJobName.md` を参照してください。
```

---

# 1. cmdlet とユーザー定義関数の違い

PowerShell のコードを読むとき、最初に混乱しやすいのがこれです。

```powershell
Import-Module
Invoke-FoundationEntrypoint
Test-Path
Import-FoundationConfig
Get-Command
Resolve-FoundationRoot
```

全部同じように見えます。
でも、実際には大きく2種類あります。

---

## 1.1 cmdlet とは

cmdlet は、PowerShell が最初から持っている、または標準モジュールが提供している命令です。

例です。

```powershell
Import-Module
Test-Path
Join-Path
Resolve-Path
Get-Command
Get-Location
Split-Path
Import-PowerShellDataFile
Start-Sleep
```

読み方は「コマンドレット」です。

だいたい `動詞-名詞` の形をしています。

```text
Import-Module
Get-Command
Test-Path
Resolve-Path
```

ただし、この形をしているからといって、必ず cmdlet とは限りません。
ユーザー定義関数も同じ命名規則を使うからです。

---

## 1.2 ユーザー定義関数とは

ユーザー定義関数は、このプロジェクトの `.ps1` ファイル内で `function` と書いて作られている関数です。

例です。

```powershell
function Resolve-FoundationRoot {
    param([string]$RootPath = "")
    ...
}
```

このように、ソースコード内に `function 関数名` と書かれているものがユーザー定義関数です。

この起動処理に出てくるユーザー定義関数には、次のようなものがあります。

```text
Resolve-FoundationRoot
Initialize-FoundationRuntime
Import-FoundationConfig
Assert-FoundationConfig
Resolve-FoundationConfigPaths
Get-FoundationDefaultJobRegistryPath
Import-FoundationJobRegistry
Assert-FoundationJobRegistry
Assert-FoundationJobDefinition
Resolve-FoundationJobRegistryPaths
Get-FoundationJobDefinition
New-FoundationRunContext
Get-FoundationJobConfig
New-FoundationLogger
New-FoundationFileSystemService
Import-FoundationJobModule
Get-FoundationJobDefinitionValue
Get-FoundationJobCommand
Invoke-FoundationEntrypoint
Invoke-InstalledAppExportJob
Close-FoundationRunContext
```

---

## 1.3 見分け方

まずは次の基準で判別します。

```text
ソース内に function 名前 がある
  → ユーザー定義関数

ソース内に function 名前 がない
  → PowerShell 標準 cmdlet か、別モジュール由来のコマンドの可能性が高い
```

たとえば `Import-FoundationConfig` は、`Config.ps1` に定義されています。
つまりユーザー定義関数です。

一方、`Import-PowerShellDataFile` は、このプロジェクト内に `function Import-PowerShellDataFile` という定義はありません。
これは PowerShell 側の cmdlet です。

---

## 1.4 このプロジェクトで特に注意する点

このプロジェクトのユーザー定義関数も、PowerShell の標準 cmdlet と同じく `動詞-名詞` 形式で命名されています。

だから見た目だけでは判別しにくいです。

```powershell
Import-Module              # cmdlet
Import-FoundationConfig    # ユーザー定義関数

Get-Command                # cmdlet
Get-FoundationJobConfig    # ユーザー定義関数

Resolve-Path               # cmdlet
Resolve-FoundationRoot     # ユーザー定義関数
```

見た目ではなく、**ソース内に function 定義があるか**で判断してください。

# 2. ジョブ起動処理で使う PowerShell 基礎文法

ここからは、ジョブ起動処理を読むために必要な PowerShell 文法を説明します。

---

## 2.1 変数: `$名前`

PowerShell の変数は `$` で始まります。

```powershell
$JobName
$ConfigPath
$RootPath
$context
$command
```

たとえば次のコードでは、`$ConfigPath` に文字列が入ります。

```powershell
$ConfigPath = Join-Path $ScriptDirectory "config\foundation.config.psd1"
```

意味はこうです。

```text
$ScriptDirectory の下に config\foundation.config.psd1 というパスを作り、
その結果を $ConfigPath に入れる。
```

---

## 2.2 引数とパラメータ

関数に値を渡すとき、PowerShell では `-名前 値` の形をよく使います。

例です。

```powershell
Invoke-FoundationEntrypoint `
    -RootPath $ScriptDirectory `
    -ConfigPath $ConfigPath `
    -JobName $JobName `
    -JobRegistryPath $JobRegistryPath
```

これは次の意味です。

```text
Invoke-FoundationEntrypoint という関数を呼ぶ。
そのとき、
RootPath には $ScriptDirectory を渡す。
ConfigPath には $ConfigPath を渡す。
JobName には $JobName を渡す。
JobRegistryPath には $JobRegistryPath を渡す。
```

`-RootPath` や `-ConfigPath` は「パラメータ名」です。

---

## 2.3 `param(...)`

PowerShell のスクリプトや関数は、`param(...)` で受け取る引数を定義します。

`run_job.ps1` の先頭には次のような定義があります。

```powershell
param(
    [Parameter(Mandatory)][string]$JobName,
    [string]$ConfigPath = "",
    [string]$JobRegistryPath = ""
)
```

これは次の意味です。

```text
このスクリプトは、外から3つの値を受け取れる。

JobName          必須。文字列。
ConfigPath       任意。文字列。指定されなければ空文字。
JobRegistryPath  任意。文字列。指定されなければ空文字。
```

つまり、最低限こう実行する必要があります。

```powershell
.\run_job.ps1 -JobName InstalledAppExport
```

`JobName` は必須なので、省略できません。

---

## 2.4 `[Parameter(Mandatory)]`

これは「このパラメータは必須」という意味です。

```powershell
[Parameter(Mandatory)][string]$JobName
```

意味はこうです。

```text
JobName は必ず渡してください。
型は string、つまり文字列です。
```

---

## 2.5 `[string]`, `[hashtable]`, `[int]`, `[object]`

PowerShell では、変数やパラメータに型を付けられます。

```powershell
[string]$JobName
[hashtable]$Config
[int]$TotalCount
[object]$JobDefinition
```

具体的には、次の意味です。

| 型 | ざっくり意味 |
|---|---|
| `[string]` | 文字列 |
| `[int]` | 整数 |
| `[hashtable]` | キーと値の入れ物 |
| `[object]` | 何でも入り得る値 |

---

## 2.6 hashtable とは

hashtable は、「名前付きの値の集まり」です。

イメージは辞書です。

```powershell
@{
    ModulePath = 'modules\InstalledAppExport\InstalledAppExport.psm1'
    CommandName = 'Invoke-InstalledAppExportJob'
}
```

これは次のような意味です。

```text
ModulePath  という名前の値は modules\InstalledAppExport\InstalledAppExport.psm1
CommandName という名前の値は Invoke-InstalledAppExportJob
```

この値を取り出すときは、こう書けます。

```powershell
$Definition['ModulePath']
$Definition['CommandName']
```

または、条件によってはこう書けます。

```powershell
$Definition.ModulePath
$Definition.CommandName
```

このプロジェクトでは、`foundation.config.psd1` や `foundation.jobs.psd1` を読み込むと、hashtable として扱われます。

---

## 2.7 `.ps1`, `.psm1`, `.psd1` の違い

この起動処理には3種類の PowerShell ファイルが出てきます。

| 拡張子 | 役割 | このプロジェクトでの例 |
|---|---|---|
| `.ps1` | スクリプトまたは関数群 | `run_job.ps1`, `internal\Bootstrap.ps1` |
| `.psm1` | PowerShell モジュール | `Foundation.psm1`, `InstalledAppExport.psm1` |
| `.psd1` | データファイル | `foundation.config.psd1`, `foundation.jobs.psd1` |

具体的には、次の意味です。

```text
.ps1   実行する処理や関数を書くファイル
.psm1  複数の .ps1 をまとめてモジュール化するファイル
.psd1  設定値を書くファイル
```

---

## 2.8 `Import-Module`

`Import-Module` は、モジュールを読み込む cmdlet です。

```powershell
Import-Module -Name $FoundationModulePath -Force -DisableNameChecking
```

意味はこうです。

```text
$FoundationModulePath にある .psm1 ファイルを読み込む。
```

このプロジェクトでは、最初に `Foundation.psm1` を読み込みます。

`Foundation.psm1` を読み込むことで、`Invoke-FoundationEntrypoint` などの関数が使えるようになります。

---

## 2.9 dot-source: `. $path`

これはかなり重要です。

`Foundation.psm1` の中では、こういう処理があります。

```powershell
. $path
```

この先頭の `.` が dot-source です。

dot-source は次の意味です。

```text
別ファイルに書かれた関数を、今のスコープに読み込む。
```

たとえば `Foundation.psm1` は、内部で次のようなファイルを読み込みます。

```text
internal\Config.ps1
internal\JobRegistry.ps1
internal\Logging.ps1
internal\FileSystem.ps1
internal\RunContext.ps1
internal\Bootstrap.ps1
```

これにより、各ファイル内の関数が `Foundation` モジュールの中で使えるようになります。

つまり、ファイルは分かれていますが、実行時には「Foundation モジュールの関数群」として扱われます。

---

## 2.10 `Export-ModuleMember`

`Export-ModuleMember` は、モジュールの外に公開する関数を指定します。

たとえば `Foundation.psm1` では、`Invoke-FoundationEntrypoint` が公開されています。

具体的には、次の意味です。

```text
モジュール内にはたくさん関数がある。
でも、外から直接呼んでよい関数は一部だけ。
その一部を Export-ModuleMember で指定する。
```

たとえば、外から呼びたいのはこれです。

```powershell
Invoke-FoundationEntrypoint
```

逆に、内部用の関数を全部外に出す必要はありません。

---

## 2.11 `Import-PowerShellDataFile`

これは `.psd1` ファイルを読み込む cmdlet です。

```powershell
$config = Import-PowerShellDataFile -LiteralPath $Path
```

意味はこうです。

```text
$Path にある .psd1 ファイルを読み込んで、
PowerShell のデータとして $config に入れる。
```

このプロジェクトでは、主に次の2つを読みます。

```text
foundation.config.psd1
foundation.jobs.psd1
```

---

## 2.12 `Test-Path`

`Test-Path` は、ファイルやフォルダが存在するか確認する cmdlet です。

```powershell
if (-not (Test-Path -LiteralPath $ConfigPath)) {
    throw "設定ファイルが見つかりません: $ConfigPath"
}
```

意味はこうです。

```text
$ConfigPath のファイルが存在しなければ、エラーにする。
```

`-not` は否定です。

```text
Test-Path が true  → 存在する
-not true          → false

Test-Path が false → 存在しない
-not false         → true
```

---

## 2.13 `throw`

`throw` は、エラーを発生させて処理を止めるために使います。

```powershell
throw "設定ファイルが見つかりません: $ConfigPath"
```

意味はこうです。

```text
これ以上処理できないので、ここで失敗として止める。
```

この起動処理では、設定ファイルがない、ジョブ定義がない、モジュールがない、関数が見つからない、などの場合に `throw` します。

---

## 2.14 `try`, `catch`, `finally`

`Invoke-FoundationEntrypoint` では、次の構造が使われています。

```powershell
try {
    # メイン処理
}
catch {
    # エラーが起きたときの処理
}
finally {
    # 成功しても失敗しても最後に実行する処理
}
```

具体的には、次の意味です。

| ブロック | 意味 |
|---|---|
| `try` | 普通に実行したい処理 |
| `catch` | エラーが起きたときの処理 |
| `finally` | 成功・失敗に関係なく最後に実行する処理 |

このプロジェクトでは、`finally` で `Close-FoundationRunContext` を呼びます。

つまり、ジョブが成功しても失敗しても、後片付けをしようとします。

---

## 2.15 call operator: `&`

ここは、PowerShell の動的実行を理解するための重要箇所です。

この起動処理で重要なのはこれです。

```powershell
$jobResult = & $command -Context $context
```

`&` は call operator と呼ばれます。

意味はこうです。

```text
$command に入っているコマンドを実行する。
```

普通は関数を直接こう呼びます。

```powershell
Invoke-InstalledAppExportJob -Context $context
```

でも、このプロジェクトでは、実行する関数名を `foundation.jobs.psd1` から動的に取得します。

そのため、最初は関数名が文字列です。

```text
CommandName = Invoke-InstalledAppExportJob
```

それを `Get-Command` で command object に変換し、最後に `&` で実行します。

流れはこうです。

```text
foundation.jobs.psd1 に CommandName = Invoke-InstalledAppExportJob と書いてある
  ↓
Get-FoundationJobCommand が Get-Command Invoke-InstalledAppExportJob を実行する
  ↓
$command に Invoke-InstalledAppExportJob の command object が入る
  ↓
& $command -Context $context で実行する
```

---

# 3. 起動処理の登場要素

この起動処理では、いくつかのファイルが登場します。

---

## 3.1 `run_job.ps1`

最初に実行されるファイルです。

役割はかなり薄いです。

やっていることは主にこれです。

```text
1. JobName などの引数を受け取る
2. Foundation.psm1 の場所を決める
3. Foundation.psm1 を Import-Module する
4. Invoke-FoundationEntrypoint を呼ぶ
```

`run_job.ps1` 自体が、InstalledAppExport の画面操作をしているわけではありません。

---

## 3.2 `Foundation.psm1`

共通基盤モジュールです。

これは「ジョブを起動するための共通部品セット」です。

中では、internal 配下のファイルを dot-source しています。

```text
Config.ps1       設定ファイルを読む係
JobRegistry.ps1  ジョブ定義を読む係
Logging.ps1      ログを書く係
FileSystem.ps1   ファイル操作の共通処理係
RunContext.ps1   Context を作る係
Bootstrap.ps1    起動全体をまとめる係
```

---

## 3.3 `foundation.config.psd1`

実行時設定ファイルです。

たとえば、次のようなものを持ちます。

```text
ログ設定
CDP 接続設定
ジョブごとの出力先
ジョブごとのタイムアウト
一時フォルダ
ダウンロード先
```

これは「どう実行するか」の設定です。

---

## 3.4 `foundation.jobs.psd1`

ジョブ定義ファイルです。

これは、「JobName と実際の関数を結びつける地図」です。

たとえば `InstalledAppExport` なら、概念的には次のような対応を持ちます。

```text
JobName: InstalledAppExport
  ModulePath:  modules\InstalledAppExport\InstalledAppExport.psm1
  CommandName: Invoke-InstalledAppExportJob
```

つまり、ユーザーが `-JobName InstalledAppExport` と指定したとき、
PowerShell はこのファイルを見て、次のことを知ります。

```text
InstalledAppExport というジョブは、InstalledAppExport.psm1 を読み込めばよい。
そして Invoke-InstalledAppExportJob を呼べばよい。
```

---

## 3.5 `Context`

`Context` は、実行に必要な情報をまとめた箱です。

これは「ジョブに渡す実行情報の入れ物」です。

中には、次のようなものが入っています。

```text
RootPath
RunId
JobName
JobDefinition
Config
CommonSettings
JobSettings
Logger
Services
Page
```

なぜ `Context` が必要かというと、関数に毎回大量の引数を渡すのは大変だからです。

たとえば `Invoke-InstalledAppExportJob` に、次のように全部渡すと読みにくくなります。

```powershell
Invoke-InstalledAppExportJob `
    -RootPath ... `
    -RunId ... `
    -Config ... `
    -JobSettings ... `
    -Logger ... `
    -FileSystem ... `
    -Browser ...
```

そこで、まとめてこうします。

```powershell
Invoke-InstalledAppExportJob -Context $context
```

# 4. 起動処理の呼び出し連鎖を読む

元の連鎖はこうです。

```text
[D0] run_job.ps1
│
├─ [D1] Import-Module modules\Foundation\Foundation.psm1
│
└─ [D1] Invoke-FoundationEntrypoint
    ├─ Resolve-FoundationRoot
    ├─ Initialize-FoundationRuntime
    ├─ Import-FoundationJobModule
    ├─ Get-FoundationJobCommand
    ├─ & $command -Context $context
    └─ Close-FoundationRunContext
```

`D0`, `D1`, `D2` は深さです。

インデントが深いほど「その中から呼ばれている」という意味です。

```text
A
└─ B
   └─ C
```

これは、次の意味です。

```text
A の中で B が呼ばれる。
B の中で C が呼ばれる。
```

---

# 5. 最初の入口: `run_job.ps1`

## 5.1 何のためのファイルか

`run_job.ps1` は、この自動化処理を開始する入口です。

ただし、ここに業務ロジックはほぼありません。

役割はこれだけです。

```text
必要な引数を受け取る
Foundation モジュールを読み込む
Foundation 側の入口関数を呼ぶ
```

---

## 5.2 呼び出される前の約束

`run_job.ps1` を使う側は、最低限 `JobName` を渡す必要があります。

例です。

```powershell
.\run_job.ps1 -JobName InstalledAppExport
```

この時点での暗黙的前提はこうです。

```text
main フォルダ配下で実行される想定である
modules\Foundation\Foundation.psm1 が存在する
config\foundation.config.psd1 が存在する
指定した JobName が foundation.jobs.psd1 に定義されている
```

---

## 5.3 行う処理

`run_job.ps1` は次の順で動きます。

```text
1. JobName / ConfigPath / JobRegistryPath を受け取る
2. $ErrorActionPreference = "Stop" にする
3. 自分自身が置かれているフォルダを $ScriptDirectory に入れる
4. ConfigPath が空なら、標準の config\foundation.config.psd1 を使う
5. Foundation.psm1 のパスを作る
6. Foundation.psm1 が存在するか確認する
7. Import-Module で Foundation.psm1 を読み込む
8. Invoke-FoundationEntrypoint を呼ぶ
```

---

## 5.4 終了後に保証すること

`run_job.ps1` が `Invoke-FoundationEntrypoint` を呼び出すところまで行けた場合、次が成立しています。

```text
Foundation.psm1 は見つかった
Foundation.psm1 は読み込まれた
Invoke-FoundationEntrypoint を呼ぶ準備ができた
```

まだ `InstalledAppExport` ジョブの中身は実行されていません。

---

# 6. `Foundation.psm1` の読み込み

## 6.1 何のためのファイルか

`Foundation.psm1` は、Foundation 共通基盤のモジュールです。

これは「起動に必要な関数セットをまとめるファイル」です。

---

## 6.2 呼び出される前の約束

`Foundation.psm1` を読み込むには、次が必要です。

```text
modules\Foundation\Foundation.psm1 が存在する
internal 配下の必要ファイルが存在する
PowerShell が .psm1 を読み込める
```

---

## 6.3 行う処理

`Foundation.psm1` は、内部で複数の `.ps1` ファイルを読み込みます。

```text
internal\Config.ps1
internal\JobRegistry.ps1
internal\Logging.ps1
internal\FileSystem.ps1
internal\RunContext.ps1
internal\Bootstrap.ps1
```

実際には、CDP や DOM 系のファイルも読み込みます。
まずは上記の起動系ファイルを押さえます。

読み込みには dot-source が使われます。

```powershell
. $path
```

---

## 6.4 終了後に保証すること

`Foundation.psm1` の読み込みが成功すると、次が成立します。

```text
Config.ps1 の関数が使える
JobRegistry.ps1 の関数が使える
RunContext.ps1 の関数が使える
Bootstrap.ps1 の関数が使える
Invoke-FoundationEntrypoint が外部から呼べる
```

ここで重要なのは、`Invoke-FoundationEntrypoint` が公開されることです。

`run_job.ps1` は、これを呼びます。

# 7. `Invoke-FoundationEntrypoint`

## 7.1 何のための関数か

`Invoke-FoundationEntrypoint` は、Foundation 側の本当の入口です。

`run_job.ps1` は薄い入口で、実際の起動手順はこの関数が担当します。

---

## 7.2 呼び出される前の約束

この関数が呼ばれる前に、次が必要です。

```text
Foundation.psm1 が import 済みである
RootPath が渡されている
ConfigPath が渡されている
JobName が渡されている
```

`JobRegistryPath` は任意です。
空なら標準の `config\foundation.jobs.psd1` を使います。

---

## 7.3 行う処理

この関数は、大きく次のことをします。

```text
1. ルートパスを確定する
2. 設定とジョブ定義を読み込んで Context を作る
3. 対象ジョブのモジュールを読み込む
4. 対象ジョブの関数を探す
5. その関数を実行する
6. エラー時はログに出す
7. 最後に後片付けする
```

コードの中心はこうです。

```powershell
$context = Initialize-FoundationRuntime ...
Import-FoundationJobModule -JobDefinition $context.JobDefinition -JobName $JobName
$command = Get-FoundationJobCommand -JobDefinition $context.JobDefinition -JobName $JobName
$jobResult = & $command -Context $context
```

具体的には、次の意味です。

```text
実行準備をする
  ↓
InstalledAppExport.psm1 を読み込む
  ↓
Invoke-InstalledAppExportJob を探す
  ↓
Invoke-InstalledAppExportJob に Context を渡して実行する
```

---

## 7.4 終了後に保証すること

正常に終われば、対象ジョブの戻り値が返ります。

失敗した場合でも、`finally` により `Close-FoundationRunContext` が呼ばれます。

つまり、次が保証されます。

```text
成功時: ジョブ実行結果が返る
失敗時: エラーログを出して、例外を再送出する
成功・失敗共通: 後片付けを試みる
```

# 32. 確認ポイント

## 32.1 `Import-FoundationConfig` と `Import-PowerShellDataFile` の違い

```powershell
Import-FoundationConfig
```

これはユーザー定義関数です。

中で、次を呼びます。

```powershell
Import-PowerShellDataFile
```

これは PowerShell の cmdlet です。

つまり関係はこうです。

```text
Import-FoundationConfig
  └─ Import-PowerShellDataFile
```

`Import-FoundationConfig` は、単に `.psd1` を読むだけではありません。
読んだあとに検証やパス解決もします。

---

## 32.2 `Import-Module` しただけで、なぜ関数が使えるのか

`.psm1` はモジュールです。

`Import-Module` で読み込むと、そのモジュールが export している関数が使えるようになります。

たとえば `Foundation.psm1` は `Invoke-FoundationEntrypoint` を export しています。

だから `run_job.ps1` から呼べます。

---

## 32.3 dot-source しただけで、なぜ別ファイルの関数が使えるのか

`Foundation.psm1` の中で、次のように internal ファイルを読み込みます。

```powershell
. $path
```

これにより、別ファイル内に書かれた `function` が、同じモジュール内の関数として見えるようになります。

つまり、ファイルは分かれていても、実行時には同じモジュールの関数群になります。

---

## 32.4 `Get-Command` は何をしているのか

`Get-Command` は、指定した名前のコマンドが存在するか探します。

この起動処理では、次を探します。

```powershell
Get-Command Invoke-InstalledAppExportJob
```

これが見つかるためには、事前に `InstalledAppExport.psm1` が import されている必要があります。

---

## 32.5 `& $command` がなぜ必要なのか

実行する関数が固定なら、こう書けばよいです。

```powershell
Invoke-InstalledAppExportJob -Context $context
```

でもこの仕組みでは、`InstalledAppExport` 以外のジョブも同じ入口から呼びたいです。

そのため、ジョブ定義から関数名を取り出し、動的に呼びます。

```powershell
& $command -Context $context
```

つまり、`&` は「変数に入っているコマンドを実行するため」に必要です。

次の質問に答えられれば、起動処理の入口を追えています。

## Q1. `run_job.ps1` は InstalledAppExport の画面操作をしているか

## Q2. `JobName = InstalledAppExport` から、なぜ `Invoke-InstalledAppExportJob` が呼ばれるのか

## Q3. `InstalledAppExport.psm1` を読み込むのはどの関数か

答え: `Import-FoundationJobModule` です。

---

## Q4. `Invoke-InstalledAppExportJob` を探すのはどの関数か

答え: `Get-FoundationJobCommand` です。

内部で `Get-Command` を使います。

---

## Q5. `Invoke-InstalledAppExportJob` を実行するコードはどこか

答え: `Invoke-FoundationEntrypoint` の中の次の行です。

```powershell
$jobResult = & $command -Context $context
```

---

## Q6. `Context` は何か

答え: ジョブに渡す情報一式です。

設定、logger、services、job definition などが入っています。

---

## Q7. `finally` は何のためか

答え: 成功しても失敗しても後片付けするためです。

# 36. 最終まとめ

この起動処理は、「受付から担当者に仕事を渡すまで」に相当します。

```text
run_job.ps1
  → 受付

Foundation.psm1
  → 共通の起動係

foundation.config.psd1
  → 実行時設定表

foundation.jobs.psd1
  → JobName と担当モジュールの対応表

Context
  → ジョブに渡す情報リュック

InstalledAppExport.psm1
  → InstalledAppExport ジョブの担当部署

Invoke-InstalledAppExportJob
  → InstalledAppExport ジョブの実作業入口
```

最重要ポイントはこれです。

```text
JobName = InstalledAppExport
  ↓
foundation.jobs.psd1 を見る
  ↓
modules\InstalledAppExport\InstalledAppExport.psm1 を読み込む
  ↓
Invoke-InstalledAppExportJob を探す
  ↓
Context を渡して実行する
```

これが起動処理の中心です。
