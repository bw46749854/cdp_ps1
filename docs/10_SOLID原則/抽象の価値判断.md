# 抽象の価値判断

この文書は、抽象を残すか消すかを判断するための横断ガイドです。
SRP / DIP の MUST 条件、例外、Job境界、Composite Job境界の正本は `main/ARCHITECTURE.md` です。
この文書では、正本の詳細ルールを再掲せず、変更前の読み方と判断手順だけを扱います。

## 1. 判断の前提

抽象とは、単にファイルや関数を増やすことではありません。
このプロジェクトで価値のある抽象は、次のいずれかを満たします。

```text
呼び出し元が知らなくてよい詳細を隠している
テスト時に差し替えられる
外部I/OやDOM操作を隔離している
業務判断を純粋に近い形で確認できる
変更理由が別のものを分けている
エラー診断を安定させている
```

判断に入る前に、まず `main/ARCHITECTURE.md` の MUST / EXCEPTION に該当するか確認します。
該当しない場合、抽象が薄く見えても、好みや一般論だけで削除しません。

## 2. 残す価値が高い抽象

| 抽象 | 残す理由 |
|---|---|
| `Dependencies.ps1` | 本番依存とテスト依存を差し替えるため |
| `DomAdapter.ps1` | WorkflowからDOM操作の詳細を隠すため |
| `DomOperations.ps1` | PowerShellとJavaScript DOM helperの境界を固定するため |
| `Rules.ps1` | 業務判断を外部I/Oなしでテストするため |
| `Reconciliation.ps1` | CSVと画面の突き合わせを独立して検証するため |
| `Output.ps1` | 出力形式変更の影響を閉じるため |
| `Download.ps1` | ダウンロード待ち、安定確認、リネームという副作用を隔離するため |
| `Models.ps1` | 結果や失敗行の形を一箇所に寄せるため |

## 3. 削除・統合を検討してよい条件

次をすべて満たす場合は、削除や統合を検討できます。

```text
1. そのファイル・関数が1行ラッパーに近い
2. 呼び出し元の知識量を減らしていない
3. テスト差し替えに使われていない
4. 変更理由が呼び出し元と完全に同じ
5. 統合しても依存方向が悪化しない
6. Architecture.Testsに反しない
```

1つでも怪しい場合は、いったん残しておく方が安全です。

## 4. 削除しない方がよい条件

次に当てはまるものは、薄く見えても削除しない方がよいです。

```text
ブラウザを隠している
DOM helperやCDPを隠している
ファイルI/Oを隠している
時刻、sleep、retry、timeoutを隠している
CSVの読み書きを隠している
ダウンロード待ちを隠している
テストで差し替えるために存在している
業務判断を純粋関数として隔離している
```

## 5. 「大きいから悪い」とは限らない

`InstalledAppExport` の `RowAction.ps1` のように、大きめでも業務的に1単位として読む方が自然な場合があります。

判断基準は行数ではありません。

```text
業務的に1つのまとまりか
途中状態の後始末が必要か
分割すると流れを追いにくくならないか
分割先に自然な名前を付けられるか
```

自然な名前を付けられない分割は、理解を助けないことがあります。

## 6. 「薄いから不要」とも限らない

`DomAdapter` や `Dependencies` は、薄く見えることがあります。
しかし、それらは次の価値を持つ場合があります。

```text
呼び出し元から詳細を隠す
テスト差し替え口になる
依存方向を安定させる
将来の変更影響を狭める
```

薄さだけで不要判断をしないでください。

## 7. 変更前チェックリスト

抽象を削除・統合する前に、次を確認します。

```text
この抽象は何を隠しているか
この抽象の呼び出し元は何を知らなくて済んでいるか
この抽象を消すとWorkflowに何が漏れるか
この抽象はテストで差し替えられているか
この抽象を消すとArchitecture.Testsは落ちるか
この抽象を消した後、同じ知識が複数箇所に散らばらないか
```

## 8. 判断メモの書き方

実際に削除判断をする時は、次の形式でメモを残すとよいです。

```text
対象:
  例: ScanTargetSync/internal/Dependencies.ps1

現在の役割:
  Workflowが使う依存一式を作る。

隠しているもの:
  DomAdapter、Output、CSV読み込み、テスト差し替え口。

削除した場合の影響:
  RunnerまたはWorkflowが個別依存を直接知る。

判断:
  残す。

理由:
  テスト差し替えと依存方向維持に価値がある。
```

このように書くと、SOLID原則の名前ではなく、実際の価値で判断できます。

## 9. この文書を更新する条件

抽象を読む観点、判断手順、変更前チェックリストが変わった場合に更新します。
SRP / DIP の MUST 条件や例外が変わった場合は、まず `main/ARCHITECTURE.md` と `main/tests/Architecture.Tests.ps1` を更新します。
この文書へ正本の詳細ルールをコピーしないでください。
