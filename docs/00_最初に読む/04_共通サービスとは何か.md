# 共通サービスとは何か

## 1. このドキュメントの目的

このプロジェクトでは、各ジョブが直接すべての処理を持っているわけではありません。

例えば、`InstalledAppExport` ジョブはCSVをダウンロードしますが、ディレクトリを安全に作る処理や中身を削除する処理は、`InstalledAppExport` の中に直接書かれていません。  
`ScanTargetSync` ジョブは端末一覧をスクロールしながら処理しますが、「見えている行だけ処理して、必要なら下へスクロールする」という汎用的な走査処理は、`ScanTargetSync` 専用ではなく Foundation 共通基盤側にあります。

このような、複数ジョブから使われる横断的な道具を、このガイドでは **共通サービス** と呼びます。

## 2. どこから共通サービスに到達するか

第2回で扱った `RunContext.ps1` は、実行時に `Context` を作ります。  
その中に `Services` というプロパティがあります。

概念的には次の形です。

```text
Context
  Services
    Logger
      WriteInfo
      WriteWarning
      WriteObject
      WriteSection
    FileSystem
      InitializeOutputDirectory
      ClearDirectory
      AssertSafeDirectory
      TestPathUnderDirectory
      RemoveFileIfExists
    Workflow
      InvokeScrollableList
    Browser
      OpenPage
      OpenPageMatchingIdentity
      SetDownloadDirectory
    Timing
      Now
      TimestampText
      SleepMilliseconds
```

今回扱うファイルとの対応は次の通りです。

| Services側の名前 | 実体に近いファイル | 役割 |
|---|---|---|
| `Logger` | `Logging.ps1` | 実行ログをコンソールやファイルに出す |
| `FileSystem` | `FileSystem.ps1` | 出力ディレクトリ、削除、パス安全確認を扱う |
| `Workflow.InvokeScrollableList` | `ScrollableList.ps1` | スクロール可能な一覧画面を最後まで走査する |
| `EndpointAction.TestFoundationFatalError` など | `Errors.ps1` | 続行不能な自動化エラーかどうか判定する |

## 3. なぜ直接呼ばずに Services を経由するのか

最初に混乱しやすい点は、次です。

```text
なぜ InstalledAppExport から Clear-DirectoryContentsSafely を直接呼ばないのか。
なぜ ScanTargetSync から Write-FoundationLog を直接呼ばないのか。
```

理由は、Feature module 側の関心を小さくするためです。

Feature module が本当に知りたいのは、例えば次のようなことです。

```text
一時ダウンロードフォルダを空にしたい
失敗CSVを書き出す前に古いファイルを消したい
処理状況をログに出したい
スクロール一覧を処理したい
```

Feature module が知る必要がないことは、次です。

```text
削除対象がドライブルートではないことをどう判定するか
ログファイル名を RunId 付きでどう作るか
Add-Content にどの Encoding を指定するか
スクロール位置が変化しない場合の同一スクロール回数をどう数えるか
```

このため、`Context.Services` が中間に置かれています。

## 4. 共通サービスを読むときの注意

共通サービスのコードは、Feature module の業務用語よりも、技術的な関心が前面に出ます。

例えば `FileSystem.ps1` は「InstalledAppExport CSV」や「LastMonthInstallExtract CSV」という業務名を知りません。  
知っているのは、次のような汎用的な概念です。

```text
ディレクトリが空ではないか
ドライブルートではないか
ユーザープロファイル直下ではないか
指定ファイルが許可ディレクトリ配下か
削除対象がファイルか
```

このような共通基盤は、業務意味を知らない代わりに、安全性や再利用性を担保します。

## 5. 今回の4ファイルの位置づけ

```text
Logging.ps1
  実行状況を見えるようにする。
  障害調査時に、どのRunIdで何が起きたかを追うための基盤。

FileSystem.ps1
  ファイル削除やディレクトリ初期化を安全に行う。
  誤って危険な場所を消さないための防波堤。

Errors.ps1
  途中継続してよい失敗と、処理全体を止めるべき失敗を分ける。
  特に DOM helper 未登録や WebSocket 系エラーを fatal として扱う。

ScrollableList.ps1
  画面に一部だけ表示される一覧を、スクロールしながら重複なく処理する。
  InstalledAppExport や ScanTargetSync のような一覧処理で使われる。
```

## 6. 本ドキュメント内容の要点

```text
- Context.Services は共通道具の入口である
- Feature module は共通基盤の詳細を直接知りすぎないようにしている
- Logging は診断性、FileSystem は安全性、ScrollableList は一覧走査、Errors は継続可否判断を担当する
- これらを削除・統合すると、複数ジョブの変更影響が一気に広がる
```
