# 全体像

## このプロジェクトを一言でいうと

このプロジェクトは、PowerShellからブラウザ自動操作とCSV処理を行うジョブ実行基盤です。

大きく分けると、次の2種類のジョブがあります。

| 種類 | 例 | 内容 |
|---|---|---|
| ブラウザを使うジョブ | `DeviceListExport`, `InstalledAppExport`, `ScanTargetSync` | Chrome DevTools Protocol とDOM JavaScriptを使って画面を操作する |
| ブラウザを使わないジョブ | `LastMonthInstallExtract`, `CompositeJobs` の一部 | CSVなどのファイルを読み、加工し、結果を出力する |

実行入口は `main/run_job.ps1` です。実行時には `-JobName InstalledAppExport` のようにジョブ名を渡します。

```powershell
.\run_job.ps1 -JobName InstalledAppExport
```

この1行だけを見ると、`InstalledAppExport` という文字列がどこにつながるのか分かりません。実際には次の順番で処理がつながります。

```text
run_job.ps1
  ↓
modules/Foundation/Foundation.psm1
  ↓
Foundation/internal/Bootstrap.ps1
  ↓
config/foundation.config.psd1
config/foundation.jobs.psd1
  ↓
対象ジョブの module
  例: modules/InstalledAppExport/InstalledAppExport.psm1
  ↓
対象ジョブの公開関数
  例: Invoke-InstalledAppExportJob
```

## 主要な依存方向

このプロジェクトでは、上位のファイルが低レベルの処理を直接持たないように分割されています。

```text
実行入口
  ↓
Foundation
  ↓
各ジョブのRunner
  ↓
Workflow
  ↓
Dependencies / Port
  ↓
DomAdapter / Input / Output / Download / Rules
  ↓
DomOperations
  ↓
Foundation DomHelper / CDP
  ↓
ブラウザ内JavaScript
```

この図の意味は、次のとおりです。

- `Runner` は、ジョブの入口です。
- `Workflow` は、処理順序を管理します。
- `Rules` は、業務判断を行います。
- `Input` は、入力ファイルを読みます。
- `Output` は、結果を書き出します。
- `Download` は、ダウンロード待ちやリネームを扱います。
- `DomAdapter` は、Workflowから見える業務名の画面操作を提供します。
- `DomOperations` は、PowerShellとブラウザ内JavaScriptの境界です。
- `Foundation` は、CDP、ログ、設定、ファイルシステムなどの共通基盤です。

## `Workflow` が直接DOMやファイルを触らない理由

`Workflow` の役割は、業務処理の順序を読むための場所です。

たとえば、InstalledAppExportジョブでは次のような流れを管理します。

```text
一覧ページを開く
  ↓
対象行を走査する
  ↓
各行の詳細を開く
  ↓
アプリCSVを出力する
  ↓
成功・失敗を集計する
```

ここにDOM selector、CSVの具体的な保存処理、`Start-Sleep`、`Get-ChildItem`、CDPのHTTP/WebSocket通信などが混ざると、Workflowを読んでも業務の流れが見えなくなります。

そのため、Workflowは次のような低レベル処理を直接持たない方針です。

```text
Workflowが直接持たないもの
  - DOM selector
  - raw CDP呼び出し
  - raw DOM helper呼び出し
  - ファイル削除、ファイル移動、CSV出力などの具体I/O
  - sleepや時刻取得
  - ブラウザの通信実装
```

この制約は、単なる美学ではありません。変更影響を閉じるためです。

たとえば、CSV出力先の仕様が変わったとき、Workflowの制御フローまで触る必要があると、業務順序の不具合を混入させやすくなります。CSV出力の詳細は `Output.ps1` や `Download.ps1` に閉じ込める方が安全です。

## このプロジェクトのファイル種別

| ファイル名の傾向 | 役割 |
|---|---|
| `*.psm1` | モジュール読み込み。internalファイルをdot-sourceし、外部公開関数をExportする |
| `Runner.ps1` | ジョブの入口。Contextを受け取り、Workflowを呼び、結果出力へつなぐ |
| `Workflow*.ps1` | 処理順序、分岐、集計を担当する |
| `Dependencies.ps1` | 本番処理とテスト用差し替え処理を束ねる |
| `Rules.ps1` | 業務ルールの判定。原則として外部I/Oを持たない |
| `Reconciliation.ps1` | CSV側データとUI側データなど、複数の情報源を突き合わせる |
| `DomAdapter.ps1` | WorkflowやRowActionから見える業務名の画面操作 |
| `DomOperations.ps1` | PowerShell関数とDOM JavaScript operation名の橋渡し |
| `Download.ps1` | ダウンロード待ち、安定確認、ファイル名変更 |
| `Output.ps1` | 結果表示、CSV出力、失敗行出力 |
| `Models.ps1` | 結果オブジェクトや失敗オブジェクトの形を作る |
| `Input.ps1`, `CsvInput.ps1` | 入力ファイル探索、CSV読み込み、CSV行の解釈 |
| `dom/features/**/*.js` | ブラウザ画面のDOMを実際に探して操作するJavaScript |

## `Context` とは何か

多くの関数で `$Context` という引数が出てきます。

`Context` は、ジョブ実行中に必要な共通情報をまとめた箱です。

主な中身は次のとおりです。

```text
Context
  RootPath          : mainディレクトリの場所
  RunId             : 実行ごとのID
  JobName           : 実行中のジョブ名
  JobDefinition     : foundation.jobs.psd1 から読んだジョブ定義
  ConfigPath        : 実際に使っている設定ファイルパス
  JobRegistryPath   : 実際に使っているジョブ定義ファイルパス
  Config            : 設定全体
  CommonSettings    : 全ジョブ共通設定
  JobSettings       : 実行中ジョブ専用設定
  Logger            : ログ出力用オブジェクト
  Services          : FileSystem, Browser, Workflow, Timing などの共通サービス
  Page              : ブラウザページ/CDPセッション情報
```

`Context` があることで、各関数は毎回すべての設定値やサービスを個別引数で受け取らなくて済みます。

ただし、何でもContextへ入れてよいわけではありません。Contextは実行環境の共有情報です。業務ルールの判定結果や一時的なループ変数を入れる場所ではありません。

## `JobDefinition` と `JobSettings` の違い

この2つは混同しやすいです。

| 名前 | 由来 | 役割 |
|---|---|---|
| `JobDefinition` | `foundation.jobs.psd1` | どのモジュールを読み、どの関数を呼ぶか。DOM bundleを使うか |
| `JobSettings` | `foundation.config.psd1` | そのジョブの実行時設定。timeout、ディレクトリ、閾値など |

例として `InstalledAppExport` を考えます。

`JobDefinition` は、次のような情報を持ちます。

```text
InstalledAppExport
  ModulePath      = modules\InstalledAppExport\InstalledAppExport.psm1
  CommandName     = Invoke-InstalledAppExportJob
  DomFeaturePaths = dom\features\installed-app-export\*.js
```

一方、`JobSettings` は、次のような情報を持ちます。

```text
InstalledAppExport
  DownloadDirectory
  TempDirectory
  DownloadTimeoutSeconds
  DownloadStableSeconds
  DetailPanelCloseWaitSeconds
```

`JobDefinition` は「何を実行するか」、`JobSettings` は「どう実行するか」です。

## `Rules.ps1` と `Workflow.ps1` の違い

`Rules.ps1` は、判定そのものを書きます。

例:

```text
手動スキャンの完了が空なら対象
差分日数が閾値以上なら対象
日付が壊れていればCSVエラー
```

`Workflow.ps1` は、判定結果を使って処理を進めます。

例:

```text
CSVを読む
Rulesで対象行を抽出する
UI一覧を読む
CSVとUIを突き合わせる
対象端末のチェックをONにする
結果を出力する
```

この分離により、業務ルールだけをテストしやすくなります。ブラウザが起動していなくても、Rulesのテストは可能です。

## `DomAdapter.ps1` と `DomOperations.ps1` の違い

どちらも画面操作に関係しますが、役割が違います。

`DomAdapter.ps1` は、PowerShell側の業務名で画面操作を表します。

```text
Open-InstalledAppExportDetailPanel
Assert-InstalledAppExportDetailPanel
Open-InstalledAppExportAppTab
Click-InstalledAppExportAppCsvButton
```

`DomOperations.ps1` は、DOM JavaScriptのoperation名に近い低い層です。

```text
Invoke-InstalledAppExportDomOperation
Wait-InstalledAppExportDomOperation
Assert-InstalledAppExportDomOperationContract
```

上位のWorkflowやRowActionが `DomOperations.ps1` の低レベル関数を直接呼ぶと、JavaScript側のoperation名や契約に強く依存してしまいます。そのため、上位は原則として `DomAdapter.ps1` の業務名関数を呼びます。

## 大きいファイルや大きい関数をすぐ悪と見なさない

このプロジェクトでは、SOLID原則を機械的に適用しません。

特に `InstalledAppExport/internal/RowAction.ps1` は、複数ステップを持っていますが、これは「1台分のアプリCSV取得」という1つの業務トランザクションです。

```text
対象行を開く
  ↓
詳細パネルを確認する
  ↓
アプリタブを開く
  ↓
CSVを出力する
  ↓
ダウンロードを待つ
  ↓
リネームする
  ↓
詳細パネルを閉じる
```

この流れを無理に細かく分散させると、逆に読みづらくなります。

設計判断では、次の問いを使います。

```text
この分割は、読む人の知識量を減らしているか
この分割は、変更理由を分けているか
この分割は、テストしやすさを上げているか
この分割は、PowerShell 5.1での追跡性を悪化させていないか
```

## 読み進める順番

最初は、低レベルのCDP実装やDOM JavaScriptから読まないでください。混乱しやすいです。

推奨順序は次です。

```text
1. run_job.ps1
2. config/foundation.jobs.psd1
3. Foundation/internal/Bootstrap.ps1
4. 各ジョブの *.psm1
5. DeviceListExport の Runner / Workflow
6. InstalledAppExport の Workflow / RowAction
7. ScanTargetSync の Rules / Reconciliation / Workflow.Orchestration
8. LastMonthInstallExtract の Workflow / Rules / Input
9. CompositeJobs
10. DomAdapter / DomOperations / DOM JavaScript
11. テスト
```

今回の第1回出力では、3、6、7の代表ファイルを先に厚く説明しています。
