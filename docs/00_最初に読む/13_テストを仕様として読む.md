# テストを仕様として読む

## 1. このプロジェクトにおけるテストの位置づけ

このプロジェクトのテストは、単に「バグがないか」を確認するためだけのものではない。

特に重要なのは、次の3種類である。

```text
1. 設計境界を守るテスト
   例: Architecture.Tests.ps1

2. 業務ルールを固定するテスト
   例: ScanTargetSync.Rules.Tests.ps1, LastMonthInstallExtract.Rules.Tests.ps1

3. PowerShell側とJavaScript側の契約を守るテスト
   例: Dom.OperationRegistryContract.Tests.ps1, *.DomOperations.Tests.ps1, tests/js/*.test.js
```

最初に理解すべきことは、**テストが落ちたときに、実装を直すべきなのか、設計方針を見直すべきなのかを分けること**である。

## 2. 「仕様として読む」とは何か

テストコードを読むとき、最初から `Mock` や `Should -Be` の細部を追う必要はない。

まず見るべきなのは、`Describe`、`Context`、`It` の文章である。

PowerShellのPesterでは、典型的に次の形でテストが書かれる。

```powershell
Describe 'ScanTargetSync target rules' {
    It 'targets rows when elapsed days are greater than or equal to the threshold' {
        ...
    }
}
```

この場合、読むべき仕様は以下である。

```text
ScanTargetSync の対象判定では、経過日数が閾値以上ならON対象になる。
つまり比較条件は「>」ではなく「>=」である。
```

テストの中身を読む前に、まずこの自然文を仕様として読む。

## 3. テストが守っている主な境界

このプロジェクトでは、次の境界が重要である。

| 境界 | 意味 | 代表テスト |
|---|---|---|
| Workflow と concrete I/O の境界 | Workflowに `Import-Csv`、`Export-Csv`、`Get-Date`、`Start-Sleep`、CDP直呼びを書かない | `Architecture.Tests.ps1`, `LastMonthInstallExtract.Architecture.Tests.ps1` |
| Feature module と CDP の境界 | InstalledAppExport / ScanTargetSync / DeviceListExport が WebSocket や CDP transport を直接触らない | `Architecture.Tests.ps1`, `*.BrowserBoundary.Tests.ps1` |
| DomAdapter / DomOperations の境界 | WorkflowやRowActionは業務名の関数を呼び、raw DOM helperはDomOperationsに閉じる | `Architecture.Tests.ps1`, `*.DomOperations.Tests.ps1` |
| Rules / Reconciliation の純粋性 | 業務判断がブラウザ・DOM・ファイルI/Oに依存しない | `Architecture.Tests.ps1`, `ScanTargetSync.Rules.Tests.ps1`, `ScanTargetSync.Reconciliation.Tests.ps1` |
| PowerShell operation と JavaScript method の一致 | `DomOperations.ps1` の MethodName がDOM JS側に実在する | `Dom.OperationRegistryContract.Tests.ps1` |
| 出力先安全性 | 出力CSVや削除対象が許可ディレクトリ外に出ない | `Foundation.FileSystem.Tests.ps1`, `*.Output.Tests.ps1`, `ScanTargetSync.FileSystemBoundary.Tests.ps1` |

## 4. テストが落ちたときの読み方

テストが落ちた場合、すぐにテストを修正してはいけない。

まず次の順序で見る。

```text
1. 失敗したテスト名を見る
2. そのテストが「境界ガード」か「業務ルール」か「通常の振る舞い確認」かを分類する
3. 境界ガードなら、実装が設計方針を破っていないかを先に疑う
4. 業務ルールなら、仕様変更なのかバグなのかを確認する
5. 通常の振る舞い確認なら、入力・戻り値・副作用のどこが変わったかを確認する
```

例えば `Architecture.Tests.ps1` が落ちた場合、これは高い確率で設計境界違反である。

```text
WorkflowにGet-Dateを書いた
WorkflowからInvoke-WebRequestを呼んだ
Feature moduleからClientWebSocketを直接使った
DomOperations以外からInvoke-FoundationDomHelperMethodを呼んだ
```

このような場合、テストを緩めるのではなく、DependenciesやServices経由に戻すことを先に検討する。

## 5. 「テストを修正してよい」ケース

テスト修正が妥当になるのは、主に次のケースである。

```text
1. 業務仕様そのものが変更された
2. 出力CSVの正式な列仕様が変更された
3. DOM画面の契約が実画面変更により変更された
4. 設計方針として、依存境界を変更する合意がある
5. 古い仕様を固定していたテストが、現行仕様と明確に矛盾している
```

逆に、次の理由だけでテストを変えるべきではない。

```text
実装を楽にしたい
テストが通らないので一時的に条件を弱くしたい
直接I/Oを書いた方が早い
DOM helperを直接呼んだ方が短い
scriptblock Port が分かりにくい
```

このプロジェクトでは、分かりにくさを減らすために設計書を書くのであり、分かりにくいから境界を壊す、という順番ではない。

## 6. 初めの最小読解ルール

テストを読むときは、まず以下だけ押さえればよい。

```text
Describe = テスト対象の大きな分類
Context  = 条件や観点の分類
It       = 守りたい具体的な仕様
Should   = 実際の期待値
Mock     = 本物の外部依存を使わないための差し替え
InModuleScope = モジュール内部関数をテストするためのPester機能
```

最初からPesterを完全に理解する必要はない。  
`It '...'` の文章を仕様として読み、それがどのプロダクトファイルに対応するかを追うことが重要である。
